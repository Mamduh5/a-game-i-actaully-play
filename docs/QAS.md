## 1. Evidence and verification layers

Each result identifies the GDS section/scenario or catalog ID, change/build revision, rules/content revision, environment, seed/profile and peers where relevant, normal or debug entry point, input/commands, expected observation, actual observation, verdict and retrievable evidence. Record failures, skips, limitations and fixes. A skipped, unavailable or unresolved oracle remains unverified. Mark a test-only time jump, forced spawn or seeded fixture wherever used. Ordinary acquisition and complete-run claims require their corresponding normal player paths.

Keep five conclusions distinct in reports. **Mechanically verified** needs state/accounting assertions against a named rule. **Agent-operated gameplay verified** needs actual player inputs and observed outcomes. **Visually inspected** needs rendered frames reviewed in context. **Performance verified against established targets** needs measurements on the named configuration with agreed budgets. **Subjective experience awaiting owner evaluation** covers enjoyment, satisfaction, perceived balance and preference. Attach any applicable combination. A successful export establishes exportability. A headless check can prove accounting. Only a rendered run can demonstrate visual legibility.

| Layer | Use and purpose | Minimum evidence | Fails when |
|---|---|---|---|
| L01 · Static validation and parsing | Changed typed scripts, scenes, resources, imports or export settings. Check parse, types and reference resolution with the pinned engine | CLI/import output, changed scope, exit status and relevant warnings. For export-sensitive changes, launch the exported build | Parse/import fails, a required resource is missing, or a new diagnostic undermines the exercised path |
| L02 · Content validation | Any catalog/recipe/generation change. Include boundaries and rejection cases | GUT 9.7.1 named assertions, inputs, expected/actual values and nonzero executed test count | Wrong value or limit, missing negative case central to the change, empty discovery or failing test |
| L04 · Combat rule testing | Damage, triggers, conversion, lifecycle, ancestry and terminal order. Use isolated deterministic fixtures with representative defenses, ownership and geometry | Ordered combat trace with event IDs plus expected amounts, sources, consumption and rejected continuations | Wrong stage, duplicate payment, false contact, wrong owner, illegal continuation or legitimate child lost |
| L05 · Integration testing | Changes crossing domains, such as kill → XP/choices → Codex/receipt or displacement → hazard → faction kill | Linked pre/post states across actual boundaries, stable IDs, replayed request and resulting deltas | Local unit passes while recipient, transition, side effect or retry is wrong |
| L06 · Engine runtime | Scenes, physics queries, timers, resources, reload or startup. Record optional owner observations separately from mechanical findings | If objective evidence is missing, withhold handoff. A reported defect reopens affected checks. Subjective evaluation remains pending until the owner plays |

## 2. Risk and regression

Select checks from the changed contract and its consumers. Record why each material dependency is covered and which expensive runs were deferred. Reuse evidence only while its build, affected code/content, options and environment remain applicable. A test suite with zero discovered cases, a swallowed failure exit or an unread screenshot supplies no pass.

| Change/risk | Proportionate verification |
|---|---|
| Text or metadata confined to documentation | Verify source authority, terminology, links/anchors, traceability and repository scope. Gameplay execution is unnecessary for a claim about the document. |
| One icon, sound, localized label or binding | Validate affected imports/references. Exercise its real UI/actor at target scale or volume. For input, include ground vs panel focus and the alternate binding. Retest related tell/visibility cases when applicable. |
| One power, enemy or reward definition | Static/content and focused GUT rules, its positive/negative conditions, actual behavior in play and compatible consumers. A rank/catalyst change reopens related forms, Fusions, offers and personal verification. |
| Shared simulation, timing, generation, save or netcode | Test affected scenario families, crossing systems and retries, plus real engine/co-op/recovery checks. Keep before/after reproductions. Run targeted stress for hot paths and complete runs for changes to admission, transition, settlement or repeat play. |
| Major integration, renderer/dependency change or readiness claim | Broader regressions across consumers and existing defects. For readiness reconcile every matrix row, current evidence and repeated native solo/co-op runs. Include the lightweight compatibility smoke check on material import/shader/storage/export changes and periodically on integrated builds. Track Web exceptions separately from native readiness. |

For a defect, preserve an isolated failing seed/profile/input or trace before repair where feasible. Exercise the smallest reproducer, the ordinary player route and a counterexample that must still succeed. For a chain defect, test both the invalid loop and a long legal branch. If fixing one lifecycle changes a recipe or payout, reopen its downstream evidence.

## 5. Agent-operated gameplay and distributed tests

<a id="qas-modes"></a>

### Three verification modes

| Mode | Permitted evidence and limits |
|---|---|
| Targeted interactive MCP | Confirm project/runtime identity. Use real menu/ability/movement input, inspect relevant state before and after, record rendered frames and debugger log, reproduce a defect and its correction. Clearly identify privileged observations. |
| Supervised autonomous real-input pilot | For continuous normal play, a development-only controller observes only what the player's viewport, audible/captioned cues and legitimate UI reveal. It operates at game cadence through the same bindings, GUI and validated commands as a player. It can explore, interact, dodge, select legal rewards, rescue and reach a terminal outcome. Record pilot version, input timestamps, visible decision cues, legal profile history, build/revision, interventions and outcome. A separate observer may log hidden state for **post-run verification**. The pilot cannot read that channel, the seed, undiscovered map, hidden entities or future rewards. |
| Controlled synthetic fixtures | Narrow rule tests may create encounters, inject faults or reach extreme tiers. Full-tick acceleration is permissible only when every logical tick, contact, deadline and event is processed consistently. Label seed/state manipulation, acceleration and instrumentation. Only ordinary real-time inputs and rendered play can prove normal attainment, responsiveness and playable performance. |

Audit observation permissions with two otherwise identical player-visible states that differ only in hidden danger/recipe knowledge. Compare decisions with the same pilot RNG. Replay its inputs through the normal router and observe representative UI clicks. Invulnerability, free resources, teleportation, extra damage, weakened enemies, internal state writes or debug-only unlocks invalidate normal victory and build evidence. A supervisor may start, stop or steer through legal controls and must record interventions. No LLM call is required per movement. When MCP is unavailable, identify the equivalent actual input/observation used and any evidence still missing. [TDS pilot](TDS.md#tds-pilot)

For example, to check a physical shield, approach from the covered side, fire, then reposition to an exposed side. Capture the shield and trajectories. Inspect which collider was struck, whether it intercepted the attack, the barrier/HP deltas and the source ID on both attempts. A visually blocked shot with damage behind the shield is a mechanical failure. A correct ledger with an invisible shield tell is a presentation failure. Apply the same paired-evidence principle to reward click-through, revive position and timed hazard warnings.

For an accounting oracle, use a fixture with 100 physical offense, 100 defense, 50% reduction, 20% penetration of the remainder, K = 100 and vulnerability ×1.4. Effective defense is 40 and resolved incoming damage is 100. Against 30 eligible barrier and 50 current HP, expect 30 absorbed, 50 HP removed and 20 overkill. The eligible damage base for ordinary Vital Exchange is 50. Repeat with a full barrier and compare Reprisal eligibility. These inputs exercise the formula and do not set content balance. [GDS §§3.3–3.5, 4.3–4.4](GDS.md#gds-combat)

**Procedural evidence.** Exercise varied seeds and deliberately adversarial layouts. Preserve each generation revision, seed, instance geometry and failing route. Check a traversable path between cores from the start, the final gateway when active, every occupied realm exit and any body that must be reached. Repeat after destruction, displacement, constructs, Collapse hazards and a teammate leaving an incomplete puzzle. Walk representative routes in the rendered game using ordinary movement. Record explored vs actually visible state before/after traversal, absence of secret leakage and persistent finite stock on return. A graph invariant and an actual walk answer different questions.

**Spatial and causal adversarial cases.** Enumerate stacked candidates beyond the engine query default, including a stack entirely inside one cell, multiple shapes per entity, thin/swept blockers, identical coordinates in two realms and a sweep through a module seam. Compare IDs/TOIs and per-target outcomes with exhaustive independent enumeration. Displace into a crystal or destructible, break/remove a solid and run a same-instant child through its updated space. Reverse creation/iteration order. Distinguish fixed roots from children that see the updated index. For equal-time root waves, vary target order, numerical entity IDs, frame slicing and packet arrival. Verify current group time/physics remains fixed, later inputs wait, sockets remain live and the terminal decision appears only after eligible immediate waves. A zero-progress cycle must yield a diagnostic interruption without partial reward. A long, genuinely finite chain at its amplification ceiling must finish.

**Active world and occurrence state.** With identical accepted inputs and RNG streams, compare one observed and one distant area. Check Hunter sensing/travel, faction HP/deaths and credit, timed quests, status ticks, spawns, finite stock and persistent routes on revisit. Move a blockage across a seam and add a construct near a corpse/realm exit. Confirm clearance for a baseline rescuer. Run PR11's last-occupant and dormant-trial cases. [TDS navigation](TDS.md#tds-nav)

**Cooperative evidence.** Use distinct processes and profile stores, matching protocol/content revisions and synchronized observations by authority tick. Exercise both host-as-player and guest-as-player for asymmetric cases. The smallest peer group that can expose each interaction suffices for routine testing. Use enough rescuers to test diminishing returns, and separate simultaneous recipient/wallet claims. A single-process simulation is useful for diagnosis. A claim about network play also requires real connected processes. For native readiness exercise authorized LAN and direct IP across appropriate hosts and separate processes, including PR07's 2/3/4-player envelope. Disclose loopback-only coverage. Consumer Internet convenience, public exposure and browser multiplayer are outside the gate.

|---|---|
| Loss, delay, jitter, duplicates, out-of-order state and missing baselines | Record imposed conditions and input-to-visible correction. Exercise voluntary movement, slowed movement, knockback, Vault, dynamic blockers and telegraph lead time. Compare authoritative reconciliation/epoch, inspect filtered payloads for fog or remote leaks, and check timely counterplay on the guest. |
| Native trust and command boundaries | On authorized private test interfaces, compare an invited DTLS connection with certificate/hostname mismatch, a reused reconnect proof, an unauthorized actor command and an oversized or unrecognized message. Check refusal, bounded processing, honest peer progress and absence of credentials in traces. |
| Split realms, death, grace expiry and reconnect | Actual realm/body, elapsed waits, saved channel, dead-vs-alive control, frozen offers/Codex and shared XP. Inspect before, during and after grace. Party-size scaling stays locked. |
| Two interactions, one stock/claim | Two independent requests, one shared remaining use. Check authoritative adjudication, buyer's valid debit and rejected competitor. Repeat with two personal limits where both may succeed. |
| Late nearby player vs remote nonparticipant | Local eligibility and distinct award receipts, shared XP and separate personal mastery. Include a dead eligible teammate at final victory. Exercise PR05's corpse/disconnect and boundary cases, including a disconnected eligible final recipient. |

Interrupt host connectivity, crash/restart the process and vary checkpoint/causal completeness. ## 6. Persistence, numbers and extended-session evidence

Use disposable copies of new and representative older profiles. Compare canonical balances, applied entitlement IDs, discover/own/verify markers, upgrade costs/ranks, mastery build/context, quest stages and temporary-run fields. Check win, loss, interrupted session and cold restart. Confirm ordinary Trade Shards and builds reset between runs while committed permanent currency, discoveries and qualifying progress remain. Unique achievements pay once and legitimate repeatable completions pay separately. [GDS §§15, 19–22](GDS.md#gds-progression) · [TDS durable progression](TDS.md#tds-save) Use distinct disposable directories/profile identities for every process. Make a separate contention case deliberately point two processes at the same native profile. Keep the second writer out until the first closes or crashes and database recovery succeeds.

| Fault boundary | Acceptance observation |
|---|---|
| Important grant before authority commit, after durable issue, before/after recipient application and either side of the application acknowledgement | Inspect all six lifecycle states in TDS §6. A failed local write is pending. Lose and retry messages, then reopen both stores and switch hosts. A valid old grant pays the intended profile exactly once. Changed contents, old credential or wrong issuer/recipient cannot create a new grant. |
| Ordinary currency within a batch, at 5 s, on defeat/quit/gateway/victory and during slow or failed storage | Measure monotonic oldest-item age and amount at risk. Crash just before and after commit. Only the uncommitted ordinary interval may be lost. Under healthy operation it spans at most 5 s. All mandatory flushes retain all eligible earnings. Failure fences new exposure and never shows safely stored or completed settlement. Discrete boss/Hunter/quest/verification awards never wait for the timer. |
| Busy writer, disk full, mid-transaction process kill, backup/migration interruption and compaction | Record native DB mode/locks, reopen a consistent generation with original receipt keys. Retry older envelopes including out-of-order IDs/gaps and repeated sessions. Compaction cannot discard recoverable outstanding grants. Old receipts cannot reapply after restart. Distinguish process-kill tests from OS/power-failure tests on an appropriate disposable environment. |
| Earlier schema, renamed ID, unsupported future schema or stale/corrupt restoration | Verify consistent backup, migration, exact quantities, schema and ownership with readback. Refuse destructive overwrite, downgrade or writable fork. Missing post-backup acknowledged history remains visible as unresolved until reconciled. |
| Failure of original authority during recovery, after settlement, or permanent loss of sole issuing store | Compare uninterrupted vs resumed canonical world/clock, RNG, positions, cooldowns, commit group, frozen offers, terminal hash and receipts. If proof is incomplete, record interruption and retain settled progress. An already signed/durable surviving entitlement remains reconcilable. A destroyed sole record cannot prove a new payout. |

**Numeric oracles.** Compare native results with independent high-precision reference calculations for representative and synthetic extreme values. Exercise both sides of 25:00, exact later two-minute boundaries and GDS §23.8 rounded display references, keeping internal values unrounded. At tier 1, time-zero maximum/new-spawn HP and damage factors are 4.20 and 2.50 under the baseline, before party/region/challenge. Verify fixed regional assignment after crossing borders, increasing maximum without healing, and final-arena exclusions. Test exact lethal equality, multiple barriers, a tiny debit against huge HP, repeated small recoveries, reduced defense near zero, mixed damage and multi-level XP carry. Round-trip large amounts through network, save and summary. Inspect outcomes, comparison branches and totals for drift, saturation, nonfinite values or missing increments. Artificial extreme-tier setup proves arithmetic only. [GDS §§3–4, 21, 23](GDS.md#gds-scaling)

For a newly spawned ordinary Runic Expanse enemy at Tier 1, two initialized players and no challenge, the derived factors relative to the unmodified archetype are 4.20 × 1.25 × 1.50 = 7.875 maximum HP and 2.50 × 1.15 × 1.10 = 3.1625 activation damage. Separating the two players does not change these factors. Test neutral Collapse hazards on their own formula, and repeat against a player-driven object and the final arena to catch multiplier leakage. [GDS §§23.5–23.7](GDS.md#gds-scaling)

**Performance evidence.** Use comparable native Windows runs with recorded hardware/OS, resolution, renderer, build, scene, seed, active participants, control scheme and conditions. Include a quiet baseline, dense overworld, split active realms, autonomous factions, stacked fields/projectiles, branching kills, gateway, final encounter and repeated teardown/reentry. Include a continuous extended Collapse session under ordinary progression plus an accelerated boundary/stress fixture. Record active entity/effect counts, physics contacts vs independent oracle, queue age/high-water, work per causal group, CPU/physics/render frame-time percentiles and worst stalls, memory trend/retained objects, peer traffic and input latency. Observe whether players can steer, recognize tells and select rewards under the measured load. Compare release and instrumented captures and verify the game outcomes with cosmetic reduction on/off.

Measure the original host and each guest separately at the PR07 test envelope in one and several active realms. Include CPU utilization and step times, encoding/decoding and checkpoint cost, bytes per channel/peer, authoritative snapshot age, p50/p95/p99 input-to-visible and correction latency, and delayed telegraphs during dense Collapse. Record workload, actual link conditions, diagnostics overhead and correctness differences. These distributions are measures to collect, not passing numbers. Verify 10^400 less two unit hits plus one heal yields 10^400 − 1, two damage events of one and one actual healing. Compare canonical fractions and opaque IDs before and after save and replication, then profile limb growth with mixed denominators. [TDS numeric contract](TDS.md#tds-performance)

Label differences from an agreed machine/workload budget as regressions or measured passes. If device/FPS/latency/party-size targets or sample counts are unresolved, report raw observations, tested conditions and limitations. Never promote a fixture count or a Godot editor reading to a published support limit. Hardware-specific targets need a recorded baseline before the label **performance verified against established targets** can be used. An unplayable native session, growing backlog that changes outcomes or accumulated memory preventing another run blocks readiness regardless of a missing numerical target. ## 8. Full-content prototype readiness gate

**Stable** requires repeatable playable native solo/co-op sessions, consistent causal outcomes, recovery/settlement and successful next-run entry. **Complete** requires legal access and observed distinct behavior for the whole catalog, evidence for QA01–QA62 at their applicable layers, and the twelve categories below. **Replayable** requires all seven coverage conditions across repeated sessions and varied coherent builds. The gate qualifies the full-content build for owner evaluation.

### Readiness triage of open items

| Class | Example | How the gate treats it |
|---|---|---|
| Confirmed existing or supplemented | GDS §3.4 order, ten acquired slots, V42.2 participation, OWNER-T01–T03 and the confirmed AC/CR categories | Test as written. A contradiction blocks the affected claim. |
| Owner-authorized provisional prototype rule | PR01–PR12 under OWNER-T04, including early gateway, fresh pool, participation and guest grace | Pin the selected revision, test the positive/negative witnesses and disclose it for owner playtesting. A verified provisional rule can pass. The owner authorized the delegation, not every chosen default as final design. |
| Delegated numerical tuning | D1, O40, bounded prices/ordinary rates and release coefficients | Record value, units, affected sources and results. Provisional balance alone need not block. |
| Deferred nonessential detail | D7–D8 polish/story beyond approved functional scope, optional Web multiplayer | Record explicit scope; preserve functional readability, discovery and native cooperative systems. |
| Genuine owner-blocking decision | A material new dependency/service, expanded cost/scope, changed confirmed mechanic or intentional forfeiture of recoverable rewards | Record alternatives and precise affected approval. Continue unaffected work. For an unsettled essential detail within OWNER-T04, agents instead register a compatible provisional rule and verify it. |

An empirical unknown is work to verify. A failed essential behavior or a missing legal acquisition path still blocks the gate. [Prototype rule register](GDS.md#gds-rules)

| Readiness classification | Treatment |
|---|---|
| Blocking defect | Withhold readiness for every unresolved critical or high-impact gameplay defect. Examples include game-breaking crashes, lost/duplicated progression, unreachable approved content or victory, broken co-op/rescue, invalid infinite loops, unplayable performance or unreadable essential danger. Preserve a reproducer, impacted requirements, fix/retest evidence and an opposing control. |
| Non-blocking defect | Record impact, frequency, evidence and why complete runs/meaningful owner evaluation remain possible. Reassess cumulative effects. |
| Provisional balance concern | Identify the target, build, observations and delegated range. A powerful legal chain or unequal raw DPS can stand. A supposedly viable starter with no legal victory path warrants investigation as a blocker. |
| Deferred design detail | Cite its GDS O/D/S entry and scope. Use a versioned OWNER-T04 choice for essential delegated behavior and verify it. Withhold a full gate only for a genuinely missing essential result, failed rule or material unresolved decision. |
| Placeholder presentation | Accept when an agent verifies distinct actors, geometry, timing, critical UI and counterplay in actual play. Missing tells, inaccessible controls and misleading collision are functional failures. |
| Unverified requirement | Name the missing oracle, environment or evidence. Unverified essential scope blocks the gate. A separately disclosed optional browser target or later service does not block native prototype readiness. |

The readiness record identifies the exact candidate, rule revisions, per-ID catalog and QA01–QA62 evidence, AC01–AC12, CR1–CR7, recovery and performance measurements, and remaining defects. Attach the independent review and its reproductions. Independent review is mandatory for a readiness claim. An aggregate pass rate cannot override a missing essential observation. Separate objective results, unestablished performance targets and subjective owner evaluation.

Agents conduct all objective testing and fix in-scope defects without asking the owner to operate Godot, run GUT or reproduce routine failures. Once the gate passes, give the owner the playable build, controls, known limitations and a few optional experience prompts, such as which tells were hard to read or which builds invited another run. Agents reproduce and classify the feedback. Keep subjective impressions and objectively verified behavior independently reportable.
