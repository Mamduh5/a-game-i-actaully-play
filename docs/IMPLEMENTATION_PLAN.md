# Full-content prototype implementation plan

**Production implementation authorized on `dev` following independent architectural review of `f93725c`.** This is the delivery sequence for the native Windows full-content prototype of *A Game I Actually Play*. The plan has **8 milestones and 90 work packages** (42 systems, integration and qualification packages plus 48 content packages). Package status is tracked below and in `docs/records/<change-id>.md`; packages without a record remain **NOT STARTED**. The early playable increments test assumptions that could otherwise invalidate dozens of content entries. The delivery target is the complete catalog and **Stable, Complete and Replayable**.

The [GDD](GDD.md#gdd-prototype) governs experience and scope. The [GDS](GDS.md#gds-authority) governs behavior, catalog and owner policy. The [TDS](TDS.md#tds-decisions) governs the working architecture and dependency conditions. The [QAS](QAS.md#qas-gate) governs evidence. When an implementation convenience conflicts with a governing rule, repair the implementation or this plan. For a genuine conflict among governing decisions, apply the resolution procedure in the [agent guide](../AGENTS.md). Engineering approval, dependency qualification, implementation, verification and independent review each require their own record.

## Dependency graph and integration order

The package prerequisite columns contain the **206 direct edges** of the execution graph. Ranges include both endpoints. A prerequisite brings all of its verified ancestors. Direct edges govern eligibility. The other references in a card identify interfaces and regression obligations, including inherited prerequisites. Systems can use labeled fixtures to establish an interface before their content exists. Legal acquisition and rendered evidence remain due at the named integration gates.

| Track | Principal dependency path | Integration decision |
|---|---|---|
| Simulation and content | WP02 → WP07 → WP08. WP04 + WP07 → WP09 → WP10/WP11 → C01–C03 → WP32 → bulk builds and WP34 | Verify geometry on its own coordinate oracle. WP04 gates shared damage directly. WP14 starts on the WP01 shell and joins actual movement, rendering and combat at WP32. |
| Co-op and durability | WP02 → WP06 → WP12. WP05 + quantity/schema contracts → WP13 → WP19. WP22 → WP23 → WP24 → WP33 | Qualify the transport before replication and the store before integration. Two independent profiles, published frontiers and durable grants establish cooperative recovery. |
| Geography and encounters | WP03/WP07 → WP16/WP17 → WP18/WP25/WP26/WP27 → C19–C43 → WP35 | Validate routes with baseline movement and dynamic geometry before multiplying authored modules. Offscreen work still advances outcomes. |
| Final integration | WP34 + WP35 + terminal/account/presentation packages → WP36 → WP37–WP41 → WP42 | The longest dependency chains converge here. Complete runs depend on usable assets, ordinary inputs, settlement, content and an exported build. A fast content track cannot compensate for a failing recovery or numeric gate. |

The original 90 cards contained 408 prerequisite relationships. On the original graph 189 were already implied by other paths. This revision moves the numeric dependency from geometry to damage, brings the first pilot forward and adds the representative encounter and faction gates. Removing transitive edges from that revised graph leaves 206. All 90 IDs reach WP42, with WP01 the sole entry. Independent storage, arithmetic, tools and pilot work can progress after WP01. Authority precedes the network handshake. The visible-input encounter and the two-profile recovery increment can proceed independently. A failed gate holds its consumers.

One longest prerequisite chain contains 19 packages (18 edges). Durations, staffing and calendars are unestimated, so elapsed-time criticality is unknown. The chain is WP01 → WP02 → WP07 → WP09 → WP10 → WP20 → WP21 → WP26 → C26 → C19 → C22 → C40 → C41 → C42 → C46 → C47 → WP36 → WP37 → WP42. It connects core combat and eligibility to mechanisms, realms, bargains, optional quests, genuine unlock histories and the final candidate. The network and persistence tracks join at progression and recovery. WP37–WP41 can collect their respective evidence in parallel against the same WP36 revision. A correction that changes what they observed reopens the affected results.

## Executable work packages

Each row is a package card. Read its ID/title, dependencies, deliverable and scope, test and runtime witness, and acceptance condition together. References of the form **G**, **T** and **Q** refer to sections of [GDS.md](GDS.md), [TDS.md](TDS.md) and [QAS.md](QAS.md) respectively. **QA**, **L**, **AC** and **CR** identify rows in QAS. The milestone references also apply. Each package excludes neighboring subsystem ownership, later catalog batches, production art and new services unless its row explicitly assigns them. A fixture used to establish an interface cannot close a normal-play requirement.

**Shared execution fields.** Initial status is **NOT STARTED** for every row. Codex owns implementation and verifies through the normal entry point unless assigned otherwise in the package record. The independent non-writer handles required review. The deliverable includes the named subsystem artifact, focused automated checks or content validations, the indicated runtime capture and a tracked result against the acceptance observation. Regress the named controls and downstream consumers when their contract changes. Size is relative (S/M/L/XL). **I** requires independent review before the change counts as integrated evidence or a verified prerequisite. **R** follows QAS risk selection, becoming **I** for a material change to a protected boundary. The lane names identify safe parallel ownership after prerequisites. Rows in the same lane share a writer or explicitly split non-overlapping files/IDs. A large row can use several sessions against the same package record.

**Large packages.** Use independently reproducible checkpoints within one card. WP09 records root admission, staged debits and terminal arbitration separately. WP23/WP24 record the fault boundaries in their rows. WP35 records world subsystems before the combined split-peer run. WP38 consolidates per-ID legal witnesses already collected by content owners. WP39/WP40 retain a receipt per CR condition. A partial checkpoint leaves the package open. This preserves shared ownership and avoids duplicating catalog or run work.
